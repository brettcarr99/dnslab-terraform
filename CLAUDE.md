# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

A Terraform-managed DNS lab in AWS that simulates a full recursive DNS resolution chain, plus a constant trickle of synthetic DNS traffic and zone churn. Six EC2 instances are deployed into a single VPC and subnet, each with a static private IP:

| IP | Name | Role | Software |
|---|---|---|---|
| `10.0.1.10` | `dns-lab-root` | Authoritative for `.`, delegates `lab.` | BIND, **AXFR slave** of dnsmaster |
| `10.0.1.11` | `dns-lab-tld` | Authoritative for `lab.`, delegates `example.lab.` | BIND, **AXFR slave** of dnsmaster |
| `10.0.1.12` | `dns-lab-sld` | Authoritative for `example.lab.`, answers `www/mail/test` | BIND, **AXFR slave** of dnsmaster |
| `10.0.1.13` | `dns-lab-resolver` | Recursive resolver with lab root hints | Unbound |
| `10.0.1.14` | `dns-lab-client` | Query generator (`dns-traffic-gen`) | bind-utils |
| `10.0.1.15` | `dns-lab-dnsmaster` | **Hidden primary** for all three zones | BIND |

**Hidden-primary architecture**: dnsmaster is `type master` for `.`, `lab.` and `example.lab.`. The root/TLD/2LD servers are `type slave` and pull each zone via AXFR, authenticated with a shared TSIG key (`dns-lab-transfer`, hmac-sha256). The key is generated by `random_id.tsig_key` and templated into all four BIND configs, so it is identical across them and stable across applies as long as state survives. dnsmaster `also-notify`s each slave so changes propagate immediately.

**Zone churn generator**: `/opt/dns-update-gen.sh` on dnsmaster runs every 5 minutes from cron, issuing TSIG-authenticated `nsupdate` calls that add and remove delegations and A records across all three zones. Logs to `/var/log/dns-updates.log`. This means the lab is never static — zone serials and record sets move on their own.

**Query generator**: `dns-traffic-gen` on the client (`/usr/local/bin`, with a README at `~brettcarr/dns-traffic-gen.md`) fires queries at the resolver. Defaults to 100 queries at 100 ms; `-n 0` runs forever, `-i` sets the interval in ms, `-v` is verbose.

**Resolver**: Unbound with a one-line custom root hints file pointing `.` at the lab root server instead of the real internet roots. DNSSEC validation is off (`module-config: "iterator"`) because the lab zones are unsigned.

Cloudflare A records for `rootdns`, `tlddns`, `2lddns`, `resolver`, `client` and `dnsmaster` on `pwei.uk` are managed alongside the AWS infrastructure (TTL 60, unproxied) so public hostnames track the instance public IPs.

## Common commands

```bash
terraform init          # first time or after provider changes
terraform plan          # preview changes
terraform apply         # deploy / update
terraform destroy       # tear down everything
```

Validate user-data scripts locally (syntax only — they need a running EC2 instance to execute):

```bash
for f in user_data/*.sh; do bash -n "$f"; done
```

After apply, use the `test_commands` output to verify the chain (~2 min for user-data, plus a reboot):

```bash
terraform output test_commands
terraform output servers
```

## Key architecture notes

**User-data templating**: Each `user_data/*.sh` is a Terraform `templatefile`. Variables are injected at apply time (`${root_ip}`, `${tsig_secret}`, `${scripts_bucket}`, …). `user_data_replace_on_change = true` on every instance, so **any** change to a script or a templated value **replaces the instance**, not reboots it. Editing a shared value (e.g. `subnet_cidr`) replaces all six.

**Static private IPs**: Derived with `cidrhost(var.subnet_cidr, N)` in `locals` so they are known at plan time and can be templated into scripts before instances exist. Hosts `.10`–`.15` are reserved for the lab.

**Every script follows the same shape**: `set -euo pipefail`, tee all output to `/var/log/user-data.log` via `logger`, set hostname, `yum update -y`, create the `brettcarr` user with a hardcoded authorized_key, install packages, write config, validate (`named-checkconf` / `unbound-checkconf`), start the service, pull and run the Chronicle installer from S3, install `/etc/cron.d/dns-lab-maintenance`, publish to SNS, `reboot`.

**Slave startup race**: `root.sh`, `tld.sh` and `sld.sh` poll `nc -zw3 <dnsmaster> 53` for up to 5 minutes before starting `named`, then start anyway and let AXFR retry. Terraform has no dependency ordering between the instances, so dnsmaster may well come up last.

**S3 script bucket**: `dns-lab-scripts-<account_id>`, `force_destroy = true`, all public access blocked. `chronicled-install.sh` is uploaded with an `filemd5` etag and pulled by each instance at boot via `aws s3 cp`. Note that updating that script changes only the S3 object — it does **not** change any `user_data`, so instances are not replaced and will not re-run it until they are next rebuilt.

**Chronicle installer**: `chronicled-install.sh` is Google's vendor-supplied `install_chronicled.py` (despite the `.sh` extension), run with no arguments. Its `--error-exit-code` defaults to `0`, so a failed install does **not** trip `set -e` and abort the rest of user-data.

**Maintenance cron** on all six nodes: `yum update -y` daily at 02:00, reboot Mondays at 03:00. dnsmaster additionally runs the update generator every 5 minutes.

**SNS notifications**: Each server publishes "setup complete, rebooting now" to `dns-lab-notifications` as its last user-data step. Confirm the email subscription after the first apply or nothing is delivered.

## State and providers

- **Local state only** — `terraform.tfstate` in the repo root, gitignored, no remote backend or locking. Losing it orphans six instances and a VPC; it also holds the TSIG secret in plaintext.
- Pinned: `aws 5.100.0`, `cloudflare 4.52.7`, `random 3.9.0`. No `required_version` for Terraform itself (state was last written by 1.15.2).
- Cloudflare provider v4 is the legacy major; v5 renames `cloudflare_record` to `cloudflare_dns_record` and changes attribute names, so a version bump is a rewrite of `cloudflare.tf`, not a drop-in.

## Required tfvars

`terraform.tfvars` is gitignored. Required: `ami_id`, `key_name`, `cloudflare_api_token`, `cloudflare_zone_id`, `notification_email`. Optional overrides: `aws_region` (default `us-east-1`), `instance_type` (`t3.micro`), `vpc_cidr` (`10.0.0.0/16`), `subnet_cidr` (`10.0.1.0/24`), `ssh_allowed_cidr` (default `0.0.0.0/0` — set this to your own IP).

`ami_id` has no default and no AMI data source, so it must be a region-correct Amazon Linux 2 ID. The scripts are `yum`/`amzn2`-shaped; AL2 went end-of-life in June 2025, so moving to AL2023 means reworking package names and `systemctl` units.

## Known rough edges

- **Hardcoded IPs in `user_data/dnsmaster.sh`** (`DNSMASTER="10.0.1.15"` at line 178; `10.0.1.10/.11/.12` in the `update_zone` calls at lines 376–382) and in the client's README text. These bypass the `cidrhost` templating, so changing `subnet_cidr` silently breaks the update generator while everything else moves.
- **`ssh_allowed_cidr` defaults to `0.0.0.0/0`** — only `terraform.tfvars` keeps SSH closed.
- **Unbound has `access-control: 0.0.0.0/0 allow`** and BIND listens on `any` with `allow-query { any; }`. The only thing preventing a public open resolver is the security group restricting port 53 to `vpc_cidr`. Don't widen that ingress rule.
- No `depends_on` between dnsmaster and its slaves; the `nc` poll is the only ordering mechanism.
